# Foundation contracts

This document is the repository authority for the DT_DataCenter foundation below
`docs/PRD.md`. Its machine-readable parts are:

- `telemetry.schema.json` for environmental MQTT payloads;
- `device-status.schema.json` for MQTT device connectivity payloads;
- `current-state.schema.json` for one canonical current-state row;
- `database/migrations/foundation.sql` for PostgreSQL persistence.

The semantic contract versions are telemetry `1.0`, device status `1.0`, and current
state `1.0`; the baseline database migration identifier is `foundation`. A breaking field
or semantic change must advance the relevant protocol version without changing these
stable artifact names.
The migration target is database `DT_DataCenter`, schema `digital_twin`, using the
established owner/admin role `bagus`.

## Identity

`site_id`, `asset_id`, `device_id`, `sensor_id`, and `coordinate_system_id` are stable,
opaque machine identifiers. They use lowercase ASCII, start with an alphanumeric
character, contain only `a-z`, `0-9`, `.`, `_`, or `-`, and are at most 64 characters.
They are not derived from a display label, coordinate, database row number, or GLB node.

`rack_id` and `server_id` are not parallel identifier namespaces. They are the
`asset_id` of an asset whose `asset_type` is respectively `rack` or `server`. This keeps
one asset identity usable by PostgreSQL, telemetry, future semantic GLB bindings,
WebGL, and AR.

`boot_id` is an opaque non-empty source-generated identifier of at most 128 characters,
without surrounding whitespace or NUL. `seq` is a non-negative integer generated by
firmware that increases monotonically within one device boot.

The sensor registry binds a `sensor_id` to exactly one current `site_id`, `device_id`,
state-owning `asset_id`, `metric`, and canonical `unit`. When a physical sensor device is
also represented as an asset, `devices.asset_id` identifies it and a `contains`
relationship attaches it to its physical parent.

## Asset hierarchy

`sites` is the root registry. Every room, zone, rack, server, environmental-sensor
asset, and selected infrastructure asset has one row in `assets`. `rooms` and `zones`
are typed views of that single registry, not duplicate sources of identity.

`asset_relationships` stores the physical `contains` edge. A child has at most one
physical parent, and both ends must belong to the same site. A rack may be contained by
a room or zone; servers and selected infrastructure may be contained by a rack. No
production inventory is seeded by the migration.

## Spatial contract

The canonical world space is metres, right-handed, with `+Y` up. Source coordinate
systems may declare other units or axes, but must be registered before their values are
treated as canonical. At most one coordinate system per site is marked canonical.

`sensor_spatial` exposes:

```text
sensor_id, device_id, asset_id, coordinate_system_id,
position_x, position_y, position_z, position_verified, position_version
```

`asset_transforms` stores position in the declared coordinate-system unit, quaternion
rotation as `(rotation_x, rotation_y, rotation_z, rotation_w)`, scale as
`(scale_x, scale_y, scale_z)`, optional `model_node_id`, verification state, and
`transform_version`. Position and transform versions are appendable; one row per object
may be current.

Unverified positions and transforms remain queryable for registration diagnostics, but
must not influence a production spatial field. The migration inserts no coordinates or
transforms.

## Environmental telemetry

The MQTT topic is:

```text
dt/<site_id>/telemetry/<device_id>/<sensor_id>/<metric>
```

The payload is validated against `telemetry.schema.json`. Every topic identity
segment must equal its payload field; the payload remains canonical. Version `1.0`
currently defines these environmental metric/unit pairs:

```text
temperature / degC
humidity    / percent_rh
```

`ts` is the physical/source measurement timestamp. `received_at` is assigned from the
server clock when persistence accepts the message; a publisher cannot supply it.

The boundary order is parse JSON, validate schema version and required fields, compare
topic and payload identity, resolve the registered sensor tuple, validate metric/unit,
handle quality, assign `received_at`, then call `accept_measurement`. Quality
`invalid` is rejected and cannot enter accepted history or current state. Sensor-specific
quality and physical-range rules remain TBD.

Every received MQTT message produces one diagnostic outcome:

- `accepted`: a new historical measurement was stored;
- `duplicate`: the QoS-1 identity and canonical content already exist;
- `rejected`: validation failed, or an existing QoS-1 identity carried different
  canonical content.

Malformed and pre-persistence failures use `record_ingestion_rejection` with a stable
reason code such as `malformed-json`, `unsupported-schema-version`, `topic-mismatch`,
`unknown-identity`, `unsupported-metric-unit`, or `invalid-quality`.

## Device connectivity

Device status uses retained QoS 1 on:

```text
dt/<site_id>/device/<device_id>/status
```

The versioned payload is validated against `device-status.schema.json` and carries
`site_id`, `device_id`, `boot_id`, and `status` (`online` or `offline`). It has no sensor,
metric, measurement timestamp, or telemetry `seq`. The server records authoritative
receipt time on the matching enabled `devices` row; it never creates measurement history.
An offline status maps existing current values sourced from that device to `offline`.
Online maps only `offline` values back to `unknown`, because connectivity alone does not
prove measurement freshness. Changed projection rows use the existing canonical
current-state SSE; repeated retained status that changes no projection emits nothing.

## History, idempotency, and current state

Accepted history is append-oriented in `measurements`. PostgreSQL enforces the QoS-1
logical identity:

```text
(device_id, boot_id, seq, sensor_id, metric)
```

`accept_measurement` inserts history first and updates current state only from the
inserted row. Exact redelivery returns `duplicate`; conflicting reuse of the identity
returns `rejected`. Neither path changes history or `state_version`.

Current state is one row per `(asset_id, metric)`. The current measurement is selected by
the greatest `(source_ts, received_at, measurement_id)`, preventing an older physical
measurement from regressing the projection. Status supports `fresh`, `stale`, `offline`,
`unknown`, and `invalid`. New state starts as `unknown` because final freshness thresholds
are intentionally TBD. A real measurement or status change receives a new stable
`state_version`; a no-op update does not.

## Current-state read

The transport-independent read boundary is the PostgreSQL view
`digital_twin.current_state`:

```sql
SELECT *
FROM digital_twin.current_state
WHERE asset_id = $1
ORDER BY metric;
```

Rows conform to `current-state.schema.json` and expose the value, unit, complete source
identity, `source_ts`, `received_at`, quality, source status, `measurement_id`,
`state_version`, and `updated_at`. Zero rows means no accepted current state; consumers
must not manufacture a value.

The Node.js runtime exposes:

```text
GET /api/assets/<asset_id>/current-state
```

It returns a JSON array of current-state rows. PostgreSQL `bigint` values
`measurement_id` and `state_version` are encoded as decimal strings to preserve exact
identity; `seq` remains a JSON integer and is limited to JavaScript's exact integer
range by the telemetry schema.

Realtime consumers connect to:

```text
GET /api/current-state/events
```

The response is `text/event-stream`. Each committed current-state advance emits one
`current-state` event whose SSE `id` is the canonical `state_version` and whose `data`
is one JSON object conforming to `current-state.schema.json`. Duplicate, rejected, and
accepted out-of-order measurements that do not advance the current-state projection emit
nothing. Delivery is best-effort and has no server-side replay; after connecting or
reconnecting, a consumer reconciles through the snapshot endpoint.

`GET /health` reports process liveness. `GET /ready` reports readiness only while the
MQTT subscription is active and PostgreSQL answers the readiness query.
